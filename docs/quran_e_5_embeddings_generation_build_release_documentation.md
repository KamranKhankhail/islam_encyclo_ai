# Quran E5 Embeddings Generation — Build & Release Documentation

## Purpose
This document explains how we generate and ship **semantic embeddings** for `quran_complete.json` using **E5 (multilingual-e5-small)**. The output is designed to be:

- **High-retrieval quality** for Arabic/English/Urdu + transliteration queries.
- **Deterministic & reproducible** (stable ordering + integrity hash).
- **Mobile-friendly** (compact, fast cosine search on low-end to high-end phones).

Embeddings are generated **offline on a workstation** (GPU-accelerated when available) and then packaged into the mobile app for on-device retrieval.

---

## Model & Retrieval Protocol
### Model
- **Model:** `intfloat/multilingual-e5-small`
- **Embedding dimension:** typically 384
- **Why E5:** trained for retrieval (query/passage pairs), strong multilingual performance.

### Required prefixes
E5 expects different prefixes for best performance:
- **Documents / corpus items:** `passage: <text>`
- **User searches:** `query: <text>`

The script enforces `passage:` for verse embeddings. Your on-device query encoder must enforce `query:`.

---

## Input Data
### Required file
- `output/processed/quran_complete.json`

### Expected structure per verse
Each object should include (at minimum):
- `verse_key` (e.g., `2:255`) or `id`
- `arabic`
- optional: `transliteration`, `transliteration_alt`
- translations in:
  - `translations_english` (dictionary of translators)
  - `translations_urdu` (dictionary of translators)
  - builtin fallbacks: `translation_en_builtin`, `translation_ur_builtin`

---

## Output Artifacts
The script writes artifacts to:
- `output/processed/`

Artifacts:
1) **Embeddings matrix**
   - `verse_embeddings_e5.npy`
   - Shape: `(N, D)` where `N` is number of verses and `D` is embedding dimension.
   - Embeddings are **L2-normalized** (cosine similarity = dot product).
   - Export dtype is configurable:
     - `float16` (recommended for mobile size)
     - `float32` (max numeric fidelity)

2) **Stable row-to-verse mapping**
   - `verse_keys_e5.json`
   - A list of verse keys aligned by row index with the embeddings file.
   - This is critical so your mobile search results map correctly to verses.

3) **Build metadata + integrity**
   - `embeddings_meta_e5.json`
   - Includes model name, dim, dtype, device info, build settings, and SHA256 hash.

4) **Evaluation report (optional but generated by default)**
   - `eval_report_e5.json`
   - Recall@K and MRR@10 for a small starting “golden queries” set.
   - This is an evaluation-only artifact (not used to train the model).

## Passage Construction Strategy
We do **not** embed all 27 translations into one passage because:
- very long passages risk **model truncation**,
- too much text introduces **noise** and can reduce retrieval precision.

Instead, we embed a **bounded, high-signal** representation:
- Arabic text
- Transliteration (primary + optional alt)
- Preferred English translations (your chosen priorities)
- Preferred Urdu translations (your chosen priorities)
- Lightweight anchors (verse_key, surah names) to help navigational queries

### Preferred translators (current)
- English priority: `yusuf-ali`, `taqi-usmani`
- Urdu priority: `fatah-muhammad-jalandhari`, `maulana-muhammad-junagarhi`

All translations remain available in `quran_complete.json` for UI display; embeddings exist purely for retrieval.

## Determinism & Correctness Guarantees
The script is built to prevent silent production failures:

1) **Deterministic verse ordering**
- Verses are sorted by `verse_key` (or `id` fallback) before embedding.
- This prevents row alignment drift if upstream JSON ordering changes.

2) **Stable mapping output**
- `verse_keys_e5.json` is saved and must be shipped with embeddings.

3) **Integrity hash**
- SHA256 of the embeddings bytes is stored in `embeddings_meta_e5.json`.
- The script verifies this hash after saving.

4) **Unicode normalization**
- Arabic/Urdu text is normalized (NFKC) and whitespace is collapsed.
- This improves consistency and reduces accidental mismatches.

## GPU-First Execution
The build machine supports a powerful GPU. The script:
- detects CUDA availability,
- prints GPU info (device name, capability),
- moves the model to GPU when possible.

If CUDA is not available, it automatically falls back to CPU.

Recommended batch sizes:
- GPU: 128 (safe starting point)
- CPU: 32

You can tune these if you change models or passage length.

From your project root:

1) Ensure Python deps are installed:
- `sentence-transformers`

- `torch` with CUDA support (recommended)

2) Run the script:
- `python path/to/your_script.py`

- `output/processed/verse_keys_e5.json`
- `output/processed/embeddings_meta_e5.json`

## Mobile Integration Notes
### Query encoding protocol
When a user searches, ALWAYS encode with:
- `query: <user_text>`

Then L2-normalize the query embedding (or use the model’s `normalize_embeddings=True`).

### Similarity
Because embeddings are normalized:
- cosine similarity = dot product

Compute:
- `scores = embeddings_matrix @ query_vector`

Retrieve top-K indices, then map:
- `verse_key = verse_keys[idx]`

### Performance expectation (Qur’an only)
With ~6.2k verses, brute-force dot product is fast even on low-end devices if implemented carefully.

## Evaluation & Golden Queries (Future Hardening)
The script includes a small starter set for evaluation only. Long-term quality hardening should be telemetry-driven:
- collect anonymized queries,
- track user clicks/opens,
- promote frequent/failing queries into the golden set.

This does not affect model weights; it prevents regressions and measures improvements over time.

## Common Failure Modes & Fixes
1) Script runs on CPU unexpectedly
- Confirm `torch.cuda.is_available()` is true
- Ensure CUDA-enabled PyTorch is installed

2) Wrong verses returned on device
- Verify you shipped both `verse_embeddings_e5.npy` and `verse_keys_e5.json`
- Verify the app uses the same row alignment

3) Low quality on romanized searches
- Ensure transliteration fields are included in the passage
- Ensure query text is normalized similarly

4) Unexpected embedding drift between builds
- Confirm deterministic sorting is enabled
- Compare `sha256` values in `embeddings_meta_e5.json`

## Change Control
Any time you change:
- passage construction logic,
- translator preference lists,
- max passage length,
- model version,
- dtype,

you must rebuild embeddings and ship updated artifacts together.

Recommended versioning practice:
- keep build artifacts under a versioned folder (e.g., `v1/embeddings/...`) or include build date/version in filenames.
